Study guide · How it works

katalepsis: checking a preview with evidence

katalepsis is a CLI that runs a project's Playwright tests, or plain-English checks driven by a model, against a preview deployment. It writes a report for the pull request where every check is passed, failed, blocked or not tested, with the screenshot, video and trace behind each failure.

TypeScript · Effect · Playwright · AI SDK · MCP github.com/glamboyosa/katalepsis katalepsis.glamboyosa.xyz

What it is

A pull request gets a preview URL. Someone has to open it and check the change works. katalepsis does that check and leaves a record of it: a report folder with an HTML page, a Markdown summary for the PR, a validated manifest.json, and the evidence files.

$ katalepsis run --cwd apps/demo-form --url http://127.0.0.1:4173
katalepsis: FAILED
  2 passed, 1 failed, 0 blocked, 0 not tested
  Report: artifacts/katalepsis/2026-10-10T12-45-00-937Z-bcfc2b/report.html
  Markdown: artifacts/katalepsis/2026-10-10T12-45-00-937Z-bcfc2b/report.md

That run is against apps/demo-form, a signup form with a deliberate bug: submitting it empty shows no error.

Who decides results

Playwright decides test results, and browser assertions that katalepsis runs decide agent checks.

Two ways to check

katalepsis run

Your Playwright tests

Runs the project's existing tests with the preview URL passed in as KATALEPSIS_BASE_URL. No AI key. Playwright's own outcome stands.

katalepsis verify

Plain-English checks

A model drives a real browser through each check in checks.json, with your own OpenAI or OpenRouter key. A pass needs browser evidence.

Both write the same report folder. The MCP server exposes both to Claude Code, Codex and Cursor, plus a tool to read a report back.

For run, the project's Playwright config needs to read the URL and keep evidence on failure:

use: {
  baseURL: process.env.KATALEPSIS_BASE_URL ?? "http://localhost:3000",
  screenshot: "only-on-failure",
  video: "retain-on-failure",
  trace: "retain-on-failure",
},

Packages

katalepsis is a pnpm monorepo where each package has one job.

packages/coreResult schemas, the Playwright runner and report ingest, the evidence store, HTML and Markdown renderers
packages/agentAgent checks: browser tools, the evidence rules, OpenAI and OpenRouter models
packages/credentialsKeys from the environment or the OS keychain, plus non-secret preferences
packages/mcpThe stdio MCP server
packages/cliThe katalepsis command and its exit codes
apps/demo-formThe buggy signup form, three Playwright tests and a checks.json

A test run, start to finish

verifyWithPlaywright in packages/core/src/verify.ts does the whole run. In order:

  1. Parse the preview URL. Only http and https are allowed, credentials in the URL are refused, and query values are collected as secrets to redact.
  2. Find the project's own @playwright/test install and config.
  3. Create the run folder, artifacts/katalepsis/<run-id>/.
  4. Optionally run the project's own playwright install, so browsers match its Playwright version.
  5. List the selected tests with playwright test --list --reporter=json. With --grep or --project, list everything too, so excluded tests can be reported as not tested.
  6. Probe the preview URL. If it is down, mark every selected test blocked and skip Playwright.
  7. Otherwise run playwright test --reporter=json, normalise its report into checks, and copy the attachments into evidence/.
  8. Work out what wasn't tested, collect run errors and coverage limitations, then validate the whole manifest against the schema and write the bundle.

The heart of it is a small decision: probe first, then either run the tests or block them.

const probeAndRun = Effect.gen(function* () {
  const reachability = yield* probe.check(preview.raw, options.signal);
  if (options.signal.aborted) return notRun([CANCELLED]);
  return reachability.reachable
    ? yield* executeTests(options, selection, preview, bundleDir, secrets)
    : blockedExecution(selected.listing.tests, preview, redact(reachability.reason, secrets));
});

The run folder is an Effect resource. Playwright's scratch output inside it is deleted when the run ends, however it ends, including Ctrl-C:

const bundleDirectory = (bundleDir: string) =>
  Effect.acquireRelease(
    Effect.tryPromise({
      try: () => mkdir(path.join(bundleDir, SCRATCH), { recursive: true }),
      catch: (cause) => new ReportWriteError({ message: `Could not create ${bundleDir}: ${String(cause)}` }),
    }),
    () => Effect.promise(() => rm(path.join(bundleDir, SCRATCH), { recursive: true, force: true })),
  );

Before the bundle is written, the manifest goes through Schema.decodeUnknownEffect(VerificationRun). If katalepsis ever builds an invalid manifest, that is reported as an internal error instead of being written.

The preview probe

A dead preview is not a broken app. Without a probe, every test would fail with a network error and the report would blame the code. So katalepsis requests the URL first.

// Gateway errors mean the preview host is up but the deployment behind it is not.
const UNAVAILABLE_STATUSES = new Set([502, 503, 504]);

const response = await fetch(url, {
  redirect: "manual",
  signal: AbortSignal.any([signal, AbortSignal.timeout(PROBE_TIMEOUT_MS)]),
});
await response.body?.cancel();
return UNAVAILABLE_STATUSES.has(response.status)
  ? { reachable: false, reason: `the preview answered with HTTP ${response.status}` }
  : { reachable: true };

The timeout is 30 seconds because dev servers like Vite can be slow to answer their first request. A 404 or 500 counts as reachable: the host answered, so the tests should run and report what they find.

Four statuses

passedThe check ran and passed
failedThe check ran and found a problem with the app
blockedThe check couldn't be judged: preview down, browser missing, run cancelled, or an agent claim without evidence
not testedSkipped, filtered out, or listed by Playwright but never run. These go in a separate notTested list, not a status on a check.

Playwright's JSON report says expected, unexpected, flaky or skipped. A failing test is then classified by its last attempt's status and error message:

const classifyFailure = (status, message, previewOrigin) => {
  if (status === "interrupted") return { status: "blocked", code: "interrupted" };
  if (message !== null && BROWSER_LAUNCH_PATTERN.test(message) && !/\bexpect\(/.test(message)) {
    return { status: "blocked", code: "browser" };
  }
  // A dead third-party or API host is a real failure of the app, so only the preview's own origin blocks.
  if (message !== null && UNREACHABLE_PATTERN.test(message) && message.includes(previewOrigin)) {
    return { status: "blocked", code: "preview-unavailable" };
  }
  if (status === "timedOut") return { status: "failed", code: "timeout" };
  if (message !== null && /\bexpect\(/.test(message)) return { status: "failed", code: "assertion" };
  return { status: "failed", code: "error" };
};

The origin check matters. If your app calls an API that is down, that's your app's problem, so it stays failed. Only the preview's own origin being unreachable blocks the test. A test that passed only on retry is passed and marked flaky, with every attempt listed.

The run's status comes from its checks:

export const aggregateStatus = (checks, errors): CheckStatus => {
  if (checks.some((check) => check.status === "failed")) return "failed";
  if (checks.length === 0 || errors.length > 0) return "blocked";
  if (checks.some((check) => check.status === "blocked")) return "blocked";
  return "passed";
};

A run with nothing in it is blocked, never passed. The CLI turns the status into an exit code, so CI can branch on it:

0Every check that ran passed
1At least one check failed
2Blocked
3Usage or setup error, no report written
4The report couldn't be written

Agent checks

For behaviour nobody has written a test for, you describe the check in JSON. Every field is required, and free-form prose is rejected by the schema.

{
  "checks": [
    {
      "id": "empty-form",
      "name": "Empty form validation",
      "intent": "Submit the signup form without filling it",
      "passCondition": "A required-field error is visible"
    }
  ]
}

Two optional fields: startPath, such as "/signup", and observeOnly for checks about the page as it loads.

Each check gets its own isolated browser context and an AI SDK ToolLoopAgent. The model only acts through seven tools:

navigateOpen a path or URL on the preview. Other sites are refused.
snapshotRead the page as an accessibility tree
clickClick by role and accessible name, or by visible text
fillType into the field with this label
pressPress a key such as Enter
assertCheck the page in the browser and record the result as evidence
finishReport a verdict once, citing assertion IDs such as a1

The loop stops when the model calls finish or hits the step or token limit. The time limit is passed to agent.generate separately.

const agent = new ToolLoopAgent({
  model,
  instructions: INSTRUCTIONS,
  tools: toolsFor(session, (reported) => {
    verdict ??= reported;
  }),
  stopWhen: [isStepCount(budget.maxSteps), hasToolCall("finish"), tokenBudget(budget.maxTotalTokens, progress)],
  maxRetries: 1,
});

The defaults are 15 steps, 200,000 tokens and 120 seconds per check. A loop that ends without finish returns no verdict, and no verdict means blocked.

Tool input schemas are Effect schemas (except snapshot, which takes no input), adapted for the AI SDK through Standard Schema so the same definition validates input and produces the JSON Schema the model sees.

The evidence rule

The model's finish call is a claim. decideOutcome in packages/agent/src/outcome.ts accepts it only when the assertions it cites agree.

What each verdict needs

passed needs every cited assertion to pass, no uncited assertion failing after them, and at least one cited “visible” assertion that wasn't already visible before the agent acted. failed needs at least one cited assertion that failed. Anything else is blocked.

export const decideOutcome = (verdict, assertions, interruption, observeOnly): Outcome => {
  if (interruption !== null) return blocked(interruption.code, interruption.message);
  if (verdict === null) return blocked("no-evidence", "The agent stopped without reporting a verdict.");

  const byId = new Map(assertions.map((assertion) => [assertion.id, assertion]));
  const unknown = verdict.assertionIds.filter((id) => !byId.has(id));
  if (unknown.length > 0) {
    return blocked("no-evidence", `The agent cited assertions that never ran: ${unknown.join(", ")}.`);
  }
  // ...
  if (cited.length === 0) {
    return blocked("no-evidence", `The agent reported "${verdict.verdict}" without citing a browser assertion.`);
  }
  // ...
};

For a claimed pass, passGap looks for reasons not to believe it:

if (!cited.every((assertion) => assertion.passed)) return "The agent reported a pass, but a cited assertion failed.";
// Failed guesses before the cited evidence are normal: a model often tries a few wordings
// before it finds the real message. A failure after it means the latest evidence disagrees.
...
const shown = cited.filter((assertion) => assertion.expectation === "visible");
if (shown.length === 0) {
  return "The agent reported a pass citing only hidden or URL assertions. A pass needs something visible on the page.";
}
if (!observeOnly && shown.every((assertion) => assertion.trueAtStart === true)) {
  return "The agent reported a pass, but everything it cited was already on the page before it acted.";
}
return null;

Notice the asymmetry. Failed assertions before the cited ones are fine, because a model often guesses wording a few times. A failed assertion after them means the latest evidence disagrees, so the pass is blocked.

A claimed failure whose cited assertions all passed is also blocked. The model can't fail a check on a hunch either.

The baseline page

One cheat stays open without this: the model asserts that a heading is visible, the heading was always there, and the check “passes”. To close it, CheckSession opens the start page twice, in two browser contexts. The agent drives one. The other is never touched.

const [response] = await Promise.all([
  this.page.goto(url.href, { timeout: ACTION_TIMEOUT_MS * 3 }),
  this.baselinePage.goto(url.href, { timeout: ACTION_TIMEOUT_MS * 3 }),
]);

When the agent calls navigate, an untouched copy of that page is opened too. Every “visible” assertion runs against the agent's page, then the same locator runs against every untouched copy:

if (expectation === "visible") {
  const counts = await Promise.all(
    this.baselinePages.map((copy) => this.locate(target, true, copy).filter({ visible: true }).count()),
  );
  trueAtStart = counts.some((count) => count > 0);
  if (trueAtStart) detail = `${detail}; also visible on an untouched copy of the page`;
}

trueAtStart is what passGap reads. If everything cited was already on the untouched page, the agent didn't cause it, and the pass is blocked. Checks marked observeOnly skip that last rule because they are about the page as it loads.

Each assertion also takes a screenshot, and every tool call goes into an action log. Browser actions run through a queue, because a model can call several tools in one step and two fill calls must not race for focus:

private exclusive<A>(action: () => Promise<A>): Promise<A> {
  const next = this.queue.then(action, action);
  this.queue = next.catch(() => undefined);
  return next;
}

The origin guard

The agent's browser can't leave the preview's origin unless you add --allow-origin. Three things enforce that:

  • A route on the browser context aborts top-level navigation requests to other origins.
  • A framenavigated listener on the main frame catches redirects, which a route only sees for their first URL.
  • Popups are closed straight away, since the tools only drive the main page.
await this.context.route("**/*", async (route) => {
  const request = route.request();
  const origin = new URL(request.url()).origin;
  if (request.isNavigationRequest() && isTopLevel(request) && !this.allowedOrigins.has(origin)) {
    this.violate(origin);
    await route.abort("blockedbyclient");
    return;
  }
  await route.fallback();
});

Only navigation is blocked. The page can still load scripts, fonts and API calls from other hosts, so it behaves as it would for a real visitor.

The report bundle

artifacts/katalepsis/<run-id>/
  report.html      open in a browser; evidence is linked by relative path
  report.md        paste into the PR description or a comment
  manifest.json    the validated results, schema version 1
  evidence/<check-id>/   screenshots, videos, traces, each with its SHA-256 in the manifest
  evidence/run/playwright.log

The folder is self-contained, so it can be zipped and attached to a PR. The manifest is defined with Effect Schema. Bundle paths are their own type that refuses absolute paths and .. segments:

export const BundlePath = Schema.String.check(
  Schema.makeFilter((path: string) => isBundlePath(path) || "must be a relative path inside the report bundle"),
);

export const EvidenceFile = Schema.Struct({
  path: BundlePath,
  mimeType: Schema.String,
  kind: EvidenceKind,          // screenshot | video | trace | log
  bytes: NonNegativeInt,
  sha256: Schema.String.check(Schema.isPattern(/^[a-f0-9]{64}$/)),
  checkId: Schema.NullOr(Schema.String),
  attempt: Schema.NullOr(NonNegativeInt),
  capturedAt: Schema.String,
});

Evidence file names are generated by katalepsis, never taken from test output, and resolveInBundle refuses any write that would land outside the folder.

Redaction

Preview hosts often put bypass tokens in the query string. parsePreviewUrl keeps two versions of the URL: raw, which goes to Playwright and is never written, and display, with every query value replaced by REDACTED. Every text file in the bundle also goes through redact, which removes each secret in its plain, percent-encoded and form-encoded spellings.

const spellings = (secret: string): ReadonlyArray<string> => {
  const encoded = encodeURIComponent(secret);
  return [...new Set([secret, encoded, encoded.replace(/%20/g, "+")])];
};

Screenshots, videos and traces are not redacted, and the report says so in its coverage limitations.

Coverage limitations

Every report lists what katalepsis can't promise. For example, it can't confirm the Playwright config actually reads KATALEPSIS_BASE_URL, and the commit shown is the local HEAD, not proof the preview was built from it.

Keys

Agent checks use your own OpenAI or OpenRouter key. resolveCredential picks one up in a fixed order: a non-empty environment variable, then the OS keychain, except in CI, where only the environment counts.

const fromEnv = env[ENV_VAR[provider]]?.trim();
if (fromEnv) return { provider, source: "environment", key: Redacted.make(fromEnv) };
if (isCi(env)) return { provider, source: "missing", key: null };
const keychain = yield* Keychain;
const stored = (yield* keychain.get(provider))?.trim();

The key is wrapped in Effect's Redacted, so it prints as a placeholder in logs, errors and JSON. katalepsis auth set stores keys in the keychain under the service name katalepsis. katalepsis config writes only the provider and model to ~/.config/katalepsis/config.json, never a key.

The MCP server

katalepsis-mcp is a local stdio server built on version 2 of the MCP TypeScript SDK. It has three tools:

verification_run_testsRun the Playwright tests against baseUrl
verification_check_browserRun agent checks with the configured provider and model, or ones passed as arguments
verification_get_reportRead an earlier run as a summary, the Markdown report or the manifest

It calls the same verifyWithPlaywright and verifyWithAgent as the CLI, so the evidence rules are identical. The server-specific rules are about safety:

  • It only works inside the --root folder. A cwd outside it, symlinks included, is refused.
  • artifacts and artifacts/katalepsis must be real directories, so reports can't be written through a link to somewhere else.
  • It runs one verification at a time.
  • It never takes an API key as a tool argument. Keys come from the environment or keychain, like the CLI.
  • Runs stop after 540 seconds by default, under the 600-second client timeout the setup guide recommends, so the server reports before the client gives up.
/** Resolves a project directory and refuses anything outside the workspace root, symlinks included. */
const projectDir = async (root: string, cwd: string | undefined): Promise<string> => {
  const resolved = await realpath(path.resolve(root, cwd ?? ".")).catch(() => {
    throw new ToolError(`No such directory inside the workspace: ${cwd ?? "."}`);
  });
  if (resolved !== root && !resolved.startsWith(root + path.sep)) {
    throw new ToolError("cwd must be inside the workspace root this server was started with.");
  }
  return resolved;
};
codex mcp add katalepsis -- katalepsis-mcp --root /path/to/your-app

Where Effect fits

katalepsis uses Effect 4 in the run pipelines and data boundaries. The browser and agent code is plain TypeScript.

Uses Effect

  • Schemas for the manifest, checks.json and tool inputs
  • The run pipelines, verifyWithPlaywright and verifyWithAgent
  • Services with live layers: PlaywrightRunner, PreviewProbe, RunMetadata, Keychain
  • Tagged errors and scoped cleanup of the run folder
  • Redacted for keys

Plain TypeScript

  • The agent tool loop, which is the AI SDK's ToolLoopAgent with async/await
  • CheckSession, a class around Playwright pages
  • decideOutcome and aggregateStatus, which are pure functions
  • URL parsing and redaction

Services make the pipeline testable. A test can supply a fake PreviewProbe that says the preview is down, without starting a server:

export class PreviewProbe extends Context.Service<
  PreviewProbe,
  { readonly check: (url: string, signal: AbortSignal) => Effect.Effect<ProbeResult> }
>()("katalepsis/PreviewProbe") {}

Questions

Questions to be ready for

Why not just let the model say whether the check passed?

Models will report success they didn't see. katalepsis treats the verdict as a claim and only accepts it when browser assertions that katalepsis ran back it up. A model can choose what to assert, but whether the assertion passed comes from the page.

What's the difference between failed and blocked?

Failed means the check ran and the app is wrong. Blocked means the check couldn't be judged: the preview was down, a browser couldn't start, the run was cancelled, or an agent made a claim without evidence. Keeping them apart stops infrastructure trouble from being reported as a bug in the PR.

How do you stop an agent passing a check on text that was always there?

Untouched copies of the start page and of every page the agent navigates to. Each visible assertion is also run against them, and a pass needs at least one cited visible assertion that wasn't on any untouched copy.

Why does katalepsis never reinterpret Playwright's assertions?

The project's tests are the authority on what “working” means. katalepsis only adds classification Playwright can't know about: whether the preview itself was reachable, and whether the browser could start.

How do preview bypass tokens stay out of the report?

The raw URL goes to Playwright and is never persisted. The stored URL has its query values replaced, and every text file is scrubbed for those values in their plain and encoded forms before it is written.

What are its limits today?

It isn't on npm, there's no ready-made GitHub Action, and it hasn't been tested in CI yet. It can't confirm the preview was built from the reported commit, and screenshots, videos and traces aren't redacted.

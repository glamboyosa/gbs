Ore Streams: understanding HTTP streaming

Ore is a small TypeScript client for consuming HTTP streams. The point of this guide is not only how Ore works — it is how to talk about streaming, async generators, SSE parsing, retries, and cancellation in an interview.

TypeScript · fetch · SSE FreeCodeCamp article api/src/client.ts

ELI5

Imagine asking someone to read you a long story.

They could wait until they finish, then hand you the full text. That is a normal HTTP response.

Or they could read one sentence at a time as they go. That is a stream. Ore helps your code listen to those sentences as they arrive.

What problem Ore solves

The Fetch API makes streaming look simple:

const response = await fetch(url);
const reader = response.body?.getReader();

Real streams have edge cases the caller should not have to manage every time:

  • The response body can be missing.
  • The network can disconnect.
  • Chunks can split in awkward places.
  • The user can cancel with an AbortSignal.
  • The stream reader should always release its lock.
  • SSE has parsing rules that are easy to miss.
  • Reconnection should preserve Last-Event-ID.

Ore wraps those concerns in async generators. Callers write a loop:

for await (const chunk of stream("https://api.example.com/chat")) {
  console.log(chunk);
}

That is the core API design: hide the reader, expose the values.

Regular streams vs SSE streams

Regular stream

Chunks of bytes over time. Use for AI chat output, log tailing, long-running command output, plain text, or binary processing.

stream(url, options) yields strings or Uint8Array.

SSE stream

One-way server-to-client events over HTTP. Use for live notifications, progress, job status, feeds, and events with IDs and names.

streamSSE(url, options) yields SSEEvent objects.

interface SSEEvent {
  id: string | null;
  event: string | null;
  data: string;
  retry?: number;
}

Streaming is incremental

A normal response is usually consumed all at once with await response.json(). A stream is consumed piece by piece:

const reader = response.body.getReader();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  console.log(value);
}

Each read() gives the next chunk. A chunk is not a message. The network decides chunk boundaries. You might receive hello as he / ll / o, or several messages in one chunk. That is why parsers need buffers.

Async generators

An async generator can yield values over time. You consume it with for await...of. That shape matches streaming data.

async function* numbers() {
  yield 1;
  await delay(100);
  yield 2;
}

for await (const value of numbers()) {
  console.log(value);
}

Ore’s stream() is an async generator. The caller never sees ReadableStreamDefaultReader, TextDecoder, retry loops, or reader cleanup. The caller just loops.

export async function* stream(
  url: string,
  options?: StreamOptions
): AsyncGenerator<string | Uint8Array, void, unknown> {
  // fetch, read, yield chunks
}

stream(): regular stream flow

  1. Build request headers.
  2. Call fetch.
  3. Check response.ok and response.body.
  4. Get a reader from the body.
  5. Read chunks in a loop; decode to text if requested.
  6. Yield each chunk.
  7. Release the reader lock in finally.
  8. Retry on failure unless the request was intentionally aborted.
const response = await fetch(url, { method: "GET", headers, signal });

if (!response.body) {
  throw new Error("Response body is null");
}

const reader = response.body.getReader();
const decoder = new TextDecoder();

try {
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    yield decode ? decoder.decode(value, { stream: true }) : value;
  }
} finally {
  reader.releaseLock();
}

The finally block is the reliability detail. Even if the loop exits on error or cancellation, the reader lock is released.

Regular streams: what to understand deeply

response.body

A ReadableStream. It may be null, so good code checks it.

getReader()

Locks the stream to one reader. While that lock is held, other code cannot read the same stream.

reader.read()

Returns { done, value }. If done is true, the stream ended. If false, value is the next Uint8Array chunk.

TextDecoder

Network chunks are bytes. decoder.decode(value, { stream: true }) keeps decoder state across chunks. That matters when a multi-byte Unicode character is split between chunks.

decode option

decode: true yields strings. decode: false yields raw Uint8Array. Same loop, two use cases.

Retrying regular streams

let retryCount = 0;

while (retryCount <= retries) {
  try {
    // fetch and read stream
    return;
  } catch (error) {
    if (signal?.aborted) throw error;

    retryCount++;
    if (retryCount > retries) {
      throw new Error("Max retries exceeded");
    }

    await delay(1000 * retryCount);
  }
}

Two rules: if the user cancelled, do not retry. If the stream completed, return from the generator.

Interview gold

Cancellation is not failure.

What is Server-Sent Events?

SSE is a text format for streaming events from server to client over HTTP. Each event is separated by a blank line. Common fields: data, event, id, retry.

The browser has EventSource, but it only supports GET, custom headers are awkward, retry behaviour varies, and it is less flexible than fetch. Ore parses SSE on top of fetch.

streamSSE(): SSE flow

  1. Build headers; add Last-Event-ID if reconnecting.
  2. Call fetch and get the body reader.
  3. Decode chunks to text and append them to a string buffer.
  4. Split complete lines; keep the final incomplete line in the buffer.
  5. Parse SSE fields.
  6. Yield an event when a blank line ends it.
  7. Track event IDs for reconnection.
  8. Retry unless aborted, honouring the SSE retry field when present.

This is more work than a regular stream because bytes are not enough. SSE has message boundaries and fields.

Why SSE needs a buffer

Network chunks do not respect line boundaries. You might receive data: hello as da / ta: hel / lo. Parsing each chunk on its own would corrupt the event.

buffer += decoder.decode(value, { stream: true });

const lines = buffer.split(/\r\n|\r|\n/);
buffer = lines.pop() || "";

The last line may be incomplete, so Ore keeps it for the next chunk. That is one of the most important implementation details.

SSE parsing rules

switch (field) {
  case "data":
    currentEvent.data += valueStr + "\n";
    hasData = true;
    break;
  case "event":
    currentEvent.event = valueStr;
    break;
  case "id":
    if (valueStr.indexOf("\0") === -1) {
      currentEvent.id = valueStr;
    }
    break;
  case "retry":
    const retry = parseInt(valueStr, 10);
    if (!isNaN(retry)) {
      retryInterval = retry;
      currentEvent.retry = retry;
    }
    break;
}
  • Multiple data: lines are joined with newlines.
  • A blank line ends an event.
  • Lines starting with : are comments.
  • id values containing a null byte are ignored.
  • retry changes the retry interval if it is a valid number.

This is why “just split on newlines” is not enough.

Reconnection with Last-Event-ID

Each event can carry an id. Ore tracks the last ID it saw. On reconnect it sends:

if (lastEventId) {
  headers["Last-Event-ID"] = lastEventId;
}

A well-behaved server can resume from that point. The client can send the header; the server must honour it for true resumption.

stream() vs streamSSE()

Use stream()

  • You only care about raw chunks
  • AI text, logs, non-SSE servers
  • You want strings or bytes as they arrive

Use streamSSE()

  • The server sends valid SSE
  • You care about event names and IDs
  • You want Last-Event-ID and server-controlled retry

Short version: stream() is for raw chunks. streamSSE() is for structured events.

Limitation

Retries do not make every stream resumable. Raw streams usually cannot resume unless the server supports offsets. SSE resume only works if the server honours Last-Event-ID.

Interview

Questions and strong answers

What is Ore?

A TypeScript streaming client that wraps fetch streams in async generators. It supports raw chunk streaming with stream() and Server-Sent Events parsing with streamSSE().

Why use async generators?

They match the shape of streaming data. Values arrive over time, so callers use for await...of instead of managing readers and loops by hand.

What is the difference between a chunk and a message?

A chunk is how the network delivers bytes. A message is an application-level unit. One message can split across chunks, and one chunk can contain several messages.

Why does SSE parsing need a buffer?

Chunks can end in the middle of a line. The parser must keep incomplete data and combine it with the next chunk before parsing.

Why call reader.releaseLock()?

getReader() locks the stream to that reader. Releasing in finally prevents leaks and runs even on errors or early exits.

Why check signal?.aborted before retrying?

An aborted signal means the caller cancelled on purpose. Retrying would fight that intent. Cancellation is not a retryable network failure.

What does TextDecoder.decode(value, { stream: true }) do?

It decodes bytes to text while preserving decoder state across chunks, so a multi-byte character split between chunks is not corrupted.

What is Last-Event-ID?

An SSE reconnection mechanism. The client sends the last event ID it processed so the server can resume from that point.

How does Ore handle retries?

stream() uses a retry count and delay. streamSSE() also respects the SSE retry field when the server provides one.

What are the limitations?

Retries are not resume. Raw streams usually restart from the beginning. SSE resume only works if the server honours Last-Event-ID.

One-minute explanation

Say this

Ore is a TypeScript library for consuming HTTP streams reliably. For regular streams it wraps fetch, reads response.body, decodes chunks if requested, and yields them through an async generator. For SSE it adds a parser for data, event, id, retry, comments, blank-line boundaries, and incomplete lines split across chunks. The design choices are async generators for a clean API, retry loops for network failures, AbortSignal for cancellation, and reader.releaseLock() for cleanup. The deepest idea: streaming is incremental — you cannot assume one network chunk equals one message.

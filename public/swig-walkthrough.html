Swig: a PostgreSQL job queue in Go

Swig lets a Go app say “do this work later.” Jobs live in a normal Postgres table. Workers are goroutines. The interesting part is how transactions, row locks, notifications, and leadership fit together without Redis or RabbitMQ.

Go · PostgreSQL · queues SELECT FOR UPDATE SKIP LOCKED

What Swig is

A job queue for Go, backed by PostgreSQL. Typical work: send a welcome email after signup, resize an upload, process a webhook, generate a report, retry an unreliable API call.

Many systems use Redis, RabbitMQ, SQS, Kafka, or a managed queue. Swig uses the database you already have. Jobs are rows. Workers are processes. PostgreSQL supplies the concurrency guarantees.

Why PostgreSQL

The design bet: PostgreSQL is already a strong coordination system.

  • Transactions
  • Row-level locks
  • SELECT FOR UPDATE SKIP LOCKED
  • LISTEN / NOTIFY
  • Advisory locks
  • Indexes, JSONB, timestamps, constraints, durable storage

For many Go apps — especially small to medium systems — that is simpler than operating a separate queue.

The main user story

A user signs up. The app must create a user row and send a welcome email.

Without a shared transaction

Split writes

  1. Insert user
  2. Commit user
  3. Enqueue email

If enqueue fails, the user exists and no email is sent.

AddJobWithTx

One commit

  1. Begin transaction
  2. Insert user
  3. Insert email job into swig_jobs
  4. Commit

Both exist, or neither does.

Strongest product story

Either both the user and the job exist, or neither exists.

Worker registry

Workers are registered by job name. A worker has:

  • JobName() string — the job kind
  • Process(context.Context) error — the work
  • JSON-serialisable fields for the payload

An EmailWorker might serialise to:

{
  "to": "user@example.com",
  "subject": "Welcome",
  "body": "Thanks for joining"
}

Swig stores that JSON in PostgreSQL. A worker later pulls the row, unmarshals into the registered struct, and calls Process.

Job lifecycle

  1. Caller uses AddJob (or a Tx / batch variant).
  2. Swig checks the worker has JobName and marshals the struct to JSON.
  3. A row is inserted into swig_jobs.
  4. A PostgreSQL trigger sends NOTIFY swig_jobs.
  5. Workers wake, or keep polling / acquiring.
  6. A worker claims a job with UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING ….
  7. Status becomes processing.
  8. The Go worker runs Process(ctx).
  9. Success → completed. Failure → requeue as pending, or failed if attempts are exhausted.

Why SKIP LOCKED matters

Without it, several workers contend on the same first pending job. Some block waiting for a lock.

With SKIP LOCKED, each worker says: give me a pending job, but if another transaction already locked one, skip it and find another. Many workers can claim different jobs at once.

Distributed processing

This is the heart of Swig’s concurrency story. The lock lives in PostgreSQL, not in the Go process, so it works across machines.

UPDATE swig_jobs
SET status = 'processing'
WHERE id = (
  SELECT id FROM swig_jobs
  WHERE status = 'pending'
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;

Why LISTEN / NOTIFY matters

Polling a table every second works. It also wastes database and CPU.

After a job row is inserted, a trigger emits a notification on the swig_jobs channel. Workers wait for that wakeup, then try to process quickly.

Source of truth

LISTEN / NOTIFY is a wakeup, not the queue. The table is still the source of truth. If a notification is lost or a worker wakes late, the job remains in swig_jobs.

Why advisory locks matter

Some work should run on only one Swig instance: requeue failed jobs, recover stale processing jobs, maintain shared queue state.

Swig elects a leader with pg_try_advisory_lock(leaderLockID). Advisory locks are application-defined locks inside PostgreSQL. If a process dies or its session ends, PostgreSQL releases the lock.

Interview

Why this is a good project to discuss

Swig gives you room to talk about Go concurrency, PostgreSQL transactions and locks, distributed-systems tradeoffs, failure handling, API design, driver abstraction, operational simplicity, and honest limitations.

Why not Redis?

Redis is a strong queue. Swig’s bet is operational: if the app already has PostgreSQL, a second system is extra failure modes, extra backups, extra local setup. You trade some throughput and specialised queue features for transactional enqueue with application data and one datastore to reason about.

What does transactional enqueue buy you?

AddJobWithTx inserts the job in the same transaction as business data. You cannot commit a user without the welcome-email job, or the job without the user. Dual-write bugs disappear at the commit boundary.

How do multiple workers avoid claiming the same job?

SELECT … FOR UPDATE SKIP LOCKED. The first worker locks a pending row. The next worker skips locked rows and takes another. Locks are held for the transaction, so this works across processes.

Is NOTIFY enough to never miss a job?

No. Notifications can be missed. The table is durable; notifications are a hint to wake up. A correct worker still queries pending rows, so a lost notify only adds latency, not data loss.

What happens if a worker dies mid-job?

The row can sit in processing. The leader recovers stale processing jobs — a classic “visibility timeout” problem. Advisory locks make sure only one instance does that recovery.

How is the driver interface useful?

Swig talks to Exec, Query, transactions, and listen/notify — not to pgx or database/sql directly. Tests and alternate drivers plug in without rewriting the queue.

What would you improve next?

Be honest: throughput vs a dedicated broker, poison-message handling, delayed / scheduled jobs, observability, and the fact that Postgres NOTIFY does not queue missed messages. Name the next primitive you would add, and why it belongs in the database rather than a new system.

A strong personal explanation

Say this

I built Swig because I wanted to see how far PostgreSQL can go as a coordination primitive. The interesting part was not inserting jobs into a table. It was making multiple Go workers claim jobs safely, supporting transactional enqueueing with application data, and handling retries and leadership without adding Redis or RabbitMQ. The project taught me a lot about Go interfaces, contexts, goroutines, transaction boundaries, and PostgreSQL’s locking model.
